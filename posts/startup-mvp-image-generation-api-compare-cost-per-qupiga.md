# Startup MVP Image Generation API — Compare Cost per Accepted Node.js Catalog Record

Short answer: the cheapest image-generation API for a property-management MVP is the one with the lowest cost per image that survives three gates: a valid response, a catalog-safe asset, and a structurally correct record. A quoted cost per generation cannot answer that question because rejected images, retries, review, and orphaned objects still consume money. Put every provider behind the same contract, store immutable evidence for each attempt, and compare accepted records rather than advertised units.

This changes the purchasing question. OpenAI, Stability, Ideogram, and fal can be candidates in a trial, but none should be selected from a price column alone; the decisive number belongs to the workload, not the provider page. For a startup enriching messy property descriptions, a plausible image paired with the wrong unit, room type, or source description is a data-integrity failure.

## How should a startup MVP compare image generation API cost?

A property description is weak input. "Bright renovated studio, near transit" does not establish a floor plan, a window view, dimensions, furnishings, or even which renovation details may be depicted. The generation layer can return usable bytes while the catalog layer still has no defensible answer to a harder question: what does this asset claim about the property?

Treat the output as an uncommitted object. The first gate checks transport and decoding. The second checks the asset policy: supported media type, pixel dimensions, byte limit, and any required moderation result. The third checks the record linking that object to `property_id`, the normalized source text, prompt revision, provider attempt, and review status. Only after all three pass should the image become visible.

This is strict on purpose.

Object storage is very good at preserving the wrong file under a durable key.

A compact state machine is enough: `requested`, `received`, `validated`, `accepted`, or `rejected`. Do not overwrite an accepted object when re-running enrichment. Write a new attempt under a unique key, then move the catalog pointer in a conditional metadata update. That boundary prevents two workers from silently swapping the image while leaving the database record unchanged.

## Begin with catalog invariants

The useful comparison is operational and deliberately unglamorous. Each candidate receives the same frozen description set, prompt policy, dimensions, and acceptance rubric. The set needs examples that expose ambiguity: duplicate listings, descriptions with negation, missing room types, multilingual fragments, and text that contains claims the image must not invent.

| Gate | Failure mode | Evidence to retain | Selection signal |
|---|---|---|---|
| Response | timeout, decode failure, or missing asset | attempt ID, timestamps, response status | successful responses per attempt |
| Asset | wrong dimensions, unsupported type, or policy rejection | digest, media type, dimensions, validator result | policy-valid assets per attempt |
| Record | wrong property link, stale description, or invalid metadata | source digest, schema version, object key | accepted catalog records per attempt |
| Review | misleading property detail or unusable composition | blinded rubric and reason code | accepted records per review minute |

The denominator matters. Count every attempt initiated for the evaluation, including retries. The numerator is narrower: records that reach `accepted`. A provider that returns quickly but needs repeated generations can lose to a slower candidate even before staff review is priced in. Conversely, a strict first pass may reject more work early and save review time. This is why a universal cheapest option does not follow from a public unit price. Consider one description that says a unit has no balcony while a generated candidate depicts one: the response can be decodable, correctly sized, and inexpensive, yet it must still fail review because publication would turn an invented visual detail into a catalog claim. A retry is a new paid attempt, its object needs a retention decision, and a reviewer must inspect the replacement. The explicit trade-off is more storage metadata and a stricter write path in exchange for knowing which costs produced something the catalog can actually publish.

Count the rejection.

Do not mix prompt tuning with provider comparison. Freeze one prompt revision for a round, record it, and start another round when it changes. Otherwise the experiment attributes prompt improvement to whichever adapter happened to run later.

## Make invalid states expensive

The adapter should emit a provider-neutral candidate, while the catalog service owns validation and publication. The following Python sketch keeps generated bytes out of the database transaction and binds the stored object to its content digest. It omits provider-specific request fields intentionally; those belong in adapters and can change without weakening the catalog invariant.

```python
from dataclasses import dataclass
from hashlib import sha256
from typing import Literal

Status = Literal["received", "validated", "accepted", "rejected"]

@dataclass(frozen=True)
class Candidate:
    property_id: str
    source_digest: str
    prompt_revision: str
    media_type: str
    width: int
    height: int
    body: bytes

@dataclass(frozen=True)
class StoredCandidate:
    object_key: str
    content_digest: str
    status: Status

def validate_and_store(candidate: Candidate, object_store) -> StoredCandidate:
    if candidate.media_type not in {"image/png", "image/jpeg"}:
        raise ValueError("unsupported media type")
    if candidate.width <= 0 or candidate.height <= 0 or not candidate.body:
        raise ValueError("invalid image payload")

    digest = sha256(candidate.body).hexdigest()
    key = f"candidates/{candidate.property_id}/{digest}"
    object_store.put_if_absent(
        key=key,
        body=candidate.body,
        media_type=candidate.media_type,
        metadata={
            "source_digest": candidate.source_digest,
            "prompt_revision": candidate.prompt_revision,
        },
    )
    return StoredCandidate(key, digest, "validated")
```

The digest is an identity check, not a quality score. Keep the original response metadata and reason codes separately, with retention rules that match the organization's privacy and audit requirements. A generated asset may be reproducible only in theory; the stored bytes and recorded inputs are the evidence actually available during a dispute or regression review.

Concurrency deserves an explicit test. Two jobs can read the same stale description, generate different candidates, and both pass image validation. Publication must therefore compare the candidate's `source_digest` with the current description digest and conditionally update the catalog record. The loser remains a traceable rejected attempt rather than becoming an unexplained orphan.

## Read the evidence as a data-quality ledger

Use a thin adapter for each candidate service. OpenAI, Stability, Ideogram, and fal should all map into the same internal candidate shape; provider-specific identifiers remain diagnostic metadata, not catalog fields. This keeps a response-format change from leaking into the product schema and makes removal possible without rewriting historical records.

The trial report should show distributions and counts, not one blended score. At minimum, report initiated attempts, response failures, asset-policy failures, record failures, review rejections, latency percentiles, and total review minutes. Cost belongs beside those measures as total trial spend divided by accepted records. Do not publish a winner when sample composition differs, validation rules changed mid-run, or a material share of outcomes is still awaiting review.

There is no honest fixed ranking here. Public prices and service boundaries can change, while acceptance depends on the descriptions, image policy, dimensions, and review rubric. Re-run the frozen corpus when an adapter, prompt revision, validator, or catalog schema changes. The main limitation of this 3-gate method is that a small MVP corpus may miss rare description patterns, while a larger trial adds review delay and spend; choose the corpus boundary before looking at results. The skeptical choice is the candidate whose failure distribution the team can explain and operate, provided its accepted-record economics fit the MVP budget.

## Migrate the publication pointer last

Start with shadow writes: generate and validate candidates, but leave the existing catalog pointer untouched. Review a bounded batch, record reason codes, and confirm that rejected objects expire under an explicit retention policy. Then enable publication for a small property cohort with a kill switch at the catalog service, not inside individual adapters.

Expand only after the accepted-record rate, review load, latency, and storage growth remain within limits chosen before the trial. Keep previous accepted assets addressable during the rollback window. The final decision is compact: select no vendor by list price; select an operating envelope, verify it against the property's own messy descriptions, and publish only through a conditional, auditable catalog update.
